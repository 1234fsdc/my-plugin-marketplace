# competitor-analysis

这是一个独立的产品竞品调研 Skill，不属于 `page-testing`。它把 PM 竞品分析、Anthropic `competitive-brief` 的竞品简报框架，以及项目原先的竞品分析需求合并为一套证据驱动的研究流程。

## 适用场景

- 用户说“调研竞品”“分析竞争对手”“做竞品对比”“研究这个赛道”“找产品差异化机会”。
- 需要比较 1 个或多个产品、网站、App、SaaS、平台、硬件或功能。
- 需要产品概览、功能矩阵、定位分析、优势弱点、价格对比、用户反馈、用户流程或产品机会。
- 需要为产品路线图、MVP、定价、销售 Battle Card、投资人/管理层汇报提供依据。

只做简单名词解释、只列产品名称、只做网页搜索摘要时，不必启动完整流程。

## 核心原则

1. **先问决策，再搜资料**：先明确本次研究要支持什么决定；没有决策目标时，先使用“了解市场与找差异化机会”作为低风险默认值。
2. **默认研究 5 个直接竞品**：再补充 2–3 个间接竞品、替代方案或相邻产品；用户点名的对象优先。市场很窄时减少数量并说明原因，不能为了凑数硬加。
3. **来源优先于记忆**：当前价格、功能、模型、版本、用户数量、融资和市场状态必须联网核验。不能用模型记忆替代当前来源。
4. **入口不等于能力**：看到按钮、菜单或营销文案，只能证明入口或官方主张存在，不能直接证明完整流程、质量或稳定性。
5. **事实、反馈、推断分开**：每个重要结论必须带证据状态、来源和日期；没有充分证据就保留为“未观察到/待验证”。
6. **优劣势要诚实**：必须记录竞品真正做得好的地方和用户认可点，不能为了证明自家产品而夸大竞品弱点。
7. **结论要能行动**：最终输出必须回答应匹配什么、应差异化什么、应暂缓什么、下一步验证什么，而不是只堆功能清单。
8. **只使用公开或用户授权材料**：不绕过登录、付费墙、验证码、限流、反机器人、权限或其他技术保护，不收集私人数据。

## 工作流

### 1. 明确研究边界

从用户输入提取并记录：

- 研究对象：产品、网站、App、公司、功能或赛道。
- 我方产品：名称、阶段、目标用户；未提供时写“未提供”，不要虚构。
- 研究目标：产品规划、功能取舍、定位、定价、销售、投资人材料或市场了解。
- 重点范围：全产品、功能领域、用户流程、AI 能力、定价、增长、技术能力等。
- 地区、语言、设备和研究日期。
- 期望产物：对话简报、Markdown、矩阵、Battle Card、Word/Excel/PDF 等。

只有缺失信息会实质改变竞品集合或结论时才追问；其他情况写明假设后继续。

### 2. 建立竞品集合

先输出候选表，再开始深挖：

| 类型 | 数量 | 选择标准 |
|---|---:|---|
| 直接竞品 | 默认 5 | 同一问题、相近用户、相近购买场景 |
| 间接竞品 | 2–3 | 解决同一 Job-to-be-Done，但产品形态不同 |
| 替代方案 | 按需 | 人工流程、表格、通用工具或“不做” |
| 相邻/标杆 | 按需 | 技术、用户、渠道或体验模式可迁移 |
| 新兴威胁 | 按需 | 增长快、融资/招聘/产品动作显示方向重合 |

每个对象写“纳入理由、主要待验证问题、计划检查的来源”。

### 3. 收集证据

按目标选择来源，不要求每次都覆盖所有渠道：

- 官方网站、产品页、帮助中心、文档、API、定价页、更新日志。
- 应用商店、Chrome Web Store、Product Hunt 等公开产品页。
- 公开发布、新闻、融资、合作、招聘和公司公告。
- G2、Capterra、TrustRadius、应用评论、论坛、Reddit、Hacker News 等用户反馈。
- 用户授权的公开试用、录屏、截图或浏览器实测；遇到登录墙就记录阻塞，不绕过。
- 公开搜索、SEO/内容表现、社交账号和社区讨论，仅在与问题相关时使用。

每条证据至少记录：对象、主张、来源 URL、来源类型、访问/发布日期、可见范围、证据状态和备注。报告中的关键事实必须能回到来源台账。

### 4. 还原产品与用户流程

对每个重点竞品至少检查一个代表性任务：入口 → 设置/注册 → 核心操作 → 结果 → 编辑/确认 → 继续使用/付费 → 失败或恢复（能观察到才写）。

如果只有官网或截图，明确写“仅验证到公开表面”；不要把未进入的步骤写成完整体验。功能区域分析必须区分：入口存在、流程可用、能力质量、结果价值。

### 5. 输出竞品概览

每个竞品至少覆盖：

- 公司/产品概况、产品类别和目标用户。
- 核心 Job-to-be-Done、主要场景和价值主张。
- 定位语句、品类归属、差异化主张和证明点。
- 核心功能、用户流程、AI/模型/RAG/自动化能力（如相关）。
- 商业模式、定价、套餐、免费/付费边界和销售方式。
- 近期产品、融资、合作、招聘或市场动作。
- 客户认可、常见抱怨、迁移/流失原因和证据限制。
- 优势、弱点、威胁和对我方的启示。

### 6. 建立功能对比矩阵

先按用户任务和购买决策定义 5–10 个能力维度，再列具体能力。默认评级：

- `Strong`：深度、控制力或执行质量明显领先。
- `Adequate`：能解决常见需求，但不构成明显优势。
- `Weak`：有入口或基础能力，但存在实质限制/摩擦。
- `Absent`：有充分证据证明本次范围内没有提供。
- `Unverified`：证据不足，不能判断质量。

每个单元格同时附：证据状态、证据摘要、研究日期和“为什么对用户重要”。“未看到”不能直接写 `Absent`。

### 7. 做定位、优势弱点和竞争格局分析

定位分析至少回答：

- 它为谁服务？
- 它解决什么问题？
- 它把自己归入什么品类？
- 它承诺什么结果？
- 它声称靠什么差异化？
- 它用什么证明主张？
- 用户为什么切换过去或留下？

可以用以下句式复原定位：

> 对于 [目标用户]， [产品] 是一个 [品类]，帮助用户 [核心结果]；相比 [替代方案]，它通过 [差异化机制] 实现这一点。

将每个优势/弱点写成“判断 + 证据 + 影响”，并区分：官方主张、用户反馈、研究推断、尚未验证。

### 8. 推导产品动作

把发现归入四类：

- **Match / 保持竞争力**：行业标配或用户明确要求，优先补齐。
- **Differentiate / 差异化**：竞争者普遍做不好、我方有独特条件或能形成长期优势的方向。
- **Deprioritize / 暂缓**：看似热闹但价值低、证据弱、成本高或不符合目标用户的动作。
- **Validate / 先验证**：重要但证据不足的假设，给出访谈、原型、实测、灰度或数据验证方式。

每条建议包含：问题、目标用户、具体方案、用户价值、业务价值、优先级、指标、风险和验证方式。

## 交付格式

默认先给“结论先行”，再给证据和详细分析。完整报告按 `references/report-template.md`；证据和评级按 `references/evidence-and-ratings.md`；来源选择按 `references/source-guide.md`。

根据用户需要输出：

- 对话简报：结论、竞品表、关键差异、建议、未知项。
- 完整 Markdown 报告：竞品概览、功能矩阵、定位、优势弱点、价格、流程、机会威胁和来源台账。
- 功能领域拆解：只分析一个流程或能力，附前后状态/公开证据。
- 销售 Battle Card：竞品优势、我方差异、何时竞品胜出、常见异议和证据。
- 可编辑矩阵：Markdown 表格或用户要求的 Excel/CSV；多表格文件按对应文档 Skill 处理。

不要默认生成漂亮 HTML、PDF 或图表；除非用户要求或图表能支持明确决策。不要为了填满矩阵而编造分数。

## 质量门槛

交付前检查：

- 结论先于长篇资料。
- 重要主张都有来源、日期和证据标签。
- 当前价格、功能、套餐和模型已重新核验。
- 直接竞品、间接竞品、替代方案的边界清楚。
- 功能评级有理由，未观察到的内容没有被写成不存在。
- 优势、弱点、机会和威胁分别有依据，不把建议冒充事实。
- 用户流程、定位和产品动作能够互相对应。
- 说明访问限制、样本偏差、研究日期和数据缺口。
- 建议足够具体，能进入产品讨论或验证计划。
