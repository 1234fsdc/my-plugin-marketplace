# 证据与评级规则

## 证据状态：我们如何知道

| 标签 | 使用条件 |
|---|---|
| `Verified` | 已端到端直接观察，或权威一手来源确认了精确事实。 |
| `Indicated` | 只看到入口、控件、标签或局部步骤，完整深度未验证。 |
| `Reported` | 来自具名用户、评测、社区、研究或公开反馈；需注明样本限制。 |
| `Inferred` | 由多项证据推导出的判断，不冒充产品事实。 |
| `Not observed` | 当前证据中没有观察到；不能因此写成不存在。 |

## 能力质量：做得怎么样

| 评级 | 使用条件 |
|---|---|
| `Strong` | 有足够证据证明能力深度、控制力或结果质量明显领先。 |
| `Adequate` | 能覆盖常见需求，但存在限制或不构成差异化。 |
| `Weak` | 能力或入口存在，但有明显摩擦、缺口或失败风险。 |
| `Absent` | 只有在文档、产品实测或多条可靠证据证明本次范围内没有能力时使用。 |
| `Unverified` | 证据不足，不能判断质量。 |

## 来源优先级

1. 产品实际公开页面、官方文档、帮助中心、定价页、更新日志。
2. 官方公告、应用商店页面、公开演示、公司招聘和监管/公开文件。
3. 可信第三方评测、分析报告、应用评论和行业媒体。
4. 社区讨论、论坛、社交媒体和单条用户反馈。
5. 模型已有知识只能帮助形成搜索词，不能单独作为当前事实证据。

## 主张台账

每条关键主张建议按以下字段记录：

```text
对象:
主张:
证据状态: Verified | Indicated | Reported | Inferred | Not observed
能力评级: Strong | Adequate | Weak | Absent | Unverified
来源:
发布日期/访问日期:
适用地区/套餐/版本:
限制与反例:
```

## 评分和权重

- 只对会影响用户决策的能力评分，不做无意义的总功能数排行。
- 先定义权重，再评分；权重应反映目标用户的实际选择标准。
- 如果超过 25% 的权重缺乏可靠证据，总分只能作为方向参考，并在报告中警告。
- 评分不是事实；必须给出理由、证据状态和敏感性说明。
- 不能通过把不利维度删掉来制造“我方领先”。

## 事实边界

- 官网宣传证明“官方这样主张”，不能自动证明体验质量。
- 一个可见按钮证明入口存在，不能证明完整工作流。
- 一条差评证明一个用户报告了问题，不能证明所有用户都遇到问题。
- 定价页未列某功能，只能写“未在该定价页观察到”，不能直接写“没有该功能”。
- 没有可靠市场份额、营收或用户量来源时，写“未找到可靠公开数据”，不要估算后装成事实。
- 时效性信息必须写查询日期；变化快的价格、功能、套餐和模型应在复测时重新核验。
