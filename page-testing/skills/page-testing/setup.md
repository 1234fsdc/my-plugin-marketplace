# setup — 扫描准备（主 agent 执行一次）

## 1. 启动项目

识别技术栈 → 启动 dev server（或使用已有进程）→ 确认可访问。

**起不来就停**：dev server 启动失败、端口被占、依赖缺失——不要绕过（不要改端口硬冲、不要注释掉报错的依赖）。把失败原因报告给用户，等用户解决或给出替代入口（如已部署的测试环境地址）。项目跑不起来，后面全是空转。

## 2. 发现路由

自动扫路由配置文件和首页爬取。列出所有页面路由，无法自动判断的路由记入报告并标注「待确认」。

## 3. 理解数据模型

读 store / context / 类型定义，产出项目画像：
- 一句话定位（这是个什么项目）
- 核心数据模型（用户、商品、帖子、订单…）
- 核心 workflow（用户来了先做什么、再做什么）
- 核心实体状态机（从代码枚举/状态字段提取，如 未支付/部分支付/已支付、活跃/已过期/离线）

## 4. 备好多角色登录态

从项目自身发现角色体系（登录页/权限配置/路由守卫），至少覆盖最小权限（viewer 类）与最大权限（superadmin 类）两端。无法自动创建的标注「未测试：无法获取该角色登录态」。
凭据随派单下发，子代理按需自行登录。派单顺序：最小权限页先派（探入口），最大权限页后派（全量）。

**没有多角色体系的项目**：项目只有单一角色（无登录、或登录后人人相同）时，不要硬编造角色维度。跳过维度 6（权限与角色），在报告里标注「项目无角色体系，权限维度不适用」。**单一角色 ≠ 没有登录**：有登录仍要验登录态本身（登出确认、密码显隐、会话过期）。

> ⚠️ **登录授权边界**：子代理遇到密码输入、MFA、consent、或不明确的账号选择时，**必须停止并返回 `BLOCKED: login-required`**，不得自行猜测、不得尝试常见密码、不得代为选择账号。已有 SSO/已登录态可以自动使用。凭据只在派单 prompt 中传递，不写入项目文件、不回显在返回结果中。

## 5. 写测试数据

通过浏览器表单操作写入数据，让项目进入"有数据"状态。同时顺带测试表单功能。

- **数据量**：按项目类型至少 5-10 条，覆盖边界：空值、超长文本、特殊字符/emoji、极端数字
- **状态覆盖（通用边界之外必做）**：核心实体状态机**每个状态至少构造一条数据**——过期仍可用、状态流转后 UI 未更新、临界状态显隐这类 bug，没有对应状态的数据就永远不会浮现

### 5.5 AI 能力质量样本（项目含 AI 功能时必做）

- 准备**真实正向样本**作为质量抽测输入：含 AI 识别/诊断/生成的项目，准备对应的真实素材（图片/文档/音频等，内容事实肉眼可辨）——能力抽测断言「AI 正确读出了素材中的关键信息」，HTTP 200 不算通过
- 样本随派单下发（路径 + 图中事实清单），验收 agent 据此断言结果内容

## 6. 列任务清单（= 功能闭环清单，供任务流派单）

基于项目画像，列出用户最可能做的 3-5 件事，每件事写成一条跨页任务（如「注册→登录→发布一条内容→搜索到它」）。
**任务清单即功能闭环清单**：从画像枚举核心功能（订单管理、通知设置、资料编辑…），每个功能必须映射到一个任务，或显式标注 `skipped` + 原因（低频/需真实数据/浏览器不可达）。不许有功能既不在任务里也没被标注。

## 完成标准（四项落盘才算准备完成）

路由清单 / 项目画像 / 测试数据说明（写了什么、在哪个页面）/ 任务清单。
